# Maintenance Goblin — Project Context

## Project Overview

**Maintenance Goblin** is a lightweight Windows desktop utility that makes common Windows maintenance and diagnostic tasks easier to run and understand.

The original project started as a small Python/Tkinter script with buttons for commands such as SFC and DISM. It has since evolved toward a polished, distributable Windows application with a deliberately playful **goblin-themed identity**, while still aiming to feel trustworthy and professional.

The core philosophy is:

> Make legitimate Windows maintenance tools accessible through one friendly interface, provide useful feedback about what is happening, and avoid the misleading "one-click PC optimizer" behaviour common in questionable cleanup software.

The application should favour **built-in Windows functionality, transparency and safety** rather than registry cleaners, fake performance claims, aggressive RAM cleaners, or destructive "optimization".

# Current Functionality

Maintenance Goblin can run several Windows maintenance operations from its GUI.

### System File Checker

Runs:

`SFC /scannow`

Used to detect and repair corrupted protected Windows system files.

### DISM

Runs Windows DISM image health/repair functionality, including:

`DISM /Online /Cleanup-Image /RestoreHealth`

This complements SFC by repairing the underlying Windows component store.

### Temporary File Cleanup

Cleans appropriate temporary files while gracefully handling files that Windows/applications currently have locked.

The UI should report useful statistics such as the number of files removed and, where possible, approximate space recovered.

### Windows Disk Cleanup

Provides access to Windows' built-in disk cleanup functionality rather than implementing an unsafe custom cleaner.

### Drive Optimization

Uses the Windows optimization command.

The application must distinguish conceptually between HDD defragmentation and SSD optimization/TRIM.

It should **never blindly treat SSDs as traditional hard drives requiring defragmentation**.

### CHKDSK

CHKDSK support has been considered/added as a **read-only diagnostic scan**.

Normal automated maintenance should not silently run destructive/fixing variants such as `/f`, `/r`, or `/x`.

If repair functionality is ever exposed, it must clearly explain that the operation may require rebooting or taking the filesystem offline.

# Main UX

The original application had individual maintenance buttons.

The preferred experience evolved toward:

**one primary maintenance action → tasks run sequentially → the application explains what is happening.**

The user should never click something and then wonder whether the application has frozen.

The GUI therefore needs:

* Current task
* Overall progress
* Running/completed/failed/skipped states
* In-app feedback
* Live or progressively updated logs
* Clear final summary
* No unnecessary completion popups
* UI remaining responsive while long commands run
* Buttons disabled appropriately while conflicting tasks execute

Long-running commands must execute outside Tkinter's main UI thread.

Tkinter widgets themselves should only be updated safely from the UI thread.

---

# Feedback & Statistics

Rather than dumping raw command-line output at the user, Maintenance Goblin should translate results into useful summaries.

Examples:

* SFC: no integrity violations
* SFC: corruption detected and repaired
* SFC: corruption detected but some files could not be repaired
* DISM: component store healthy
* DISM: repair completed
* CHKDSK: filesystem healthy
* CHKDSK: potential errors detected
* Temporary files removed
* Approximate storage recovered
* Free disk space before/after
* Task duration
* Total maintenance duration

Raw command output can remain available through an expandable log/debug area.

# Administrator Privileges

Several Windows maintenance commands require elevation.

The application contains administrator detection/elevation logic.

A previous bug caused:

`_tkinter.TclError: can't invoke "tk" command: application has been destroyed`

This occurred because GUI/ttkbootstrap resources were being created around the elevation/relaunch process.

The intended architecture is:

1. Application starts.
2. Determine whether elevation is required.
3. Elevate/relaunch if necessary.
4. Only after the final process is established should the Tk/ttkbootstrap root and widgets be created.
5. `create_gui()` builds the interface.
6. `main()` owns the application lifecycle and `mainloop()`.

Avoid creating multiple Tk root instances.

# Logging

Logs should primarily be available **inside the application**.

Users should not receive modal message boxes simply saying that a log was written.

Desired behaviour:

Task running → visible status/progress → task result → log available in interface.

Logs/reports may additionally be written to an appropriate application data directory and exported manually.

Potential report information:

* Timestamp
* Maintenance Goblin version
* Windows version
* Tasks executed
* Result of each task
* Duration
* Errors/warnings
* Disk-space changes

Avoid exposing unnecessarily sensitive machine information in exported reports.

As the project matures, user-specific writable data should live somewhere such as:

Potential stored data:

* Settings

# Security & Trust

This is especially important because Maintenance Goblin:

* requests administrator privileges
* executes Windows system utilities
* deletes temporary files
* may trigger antivirus/SmartScreen warnings when unsigned

The project should therefore be unusually transparent.

Prefer:

* documented commands
* source code availability
* clear explanations
* conservative defaults
* explicit confirmation for potentially destructive operations
* no telemetry by default
* no hidden background processes
* no registry cleaning
* no fake performance claims
* no bundled software
* no advertisements
* no unnecessary network access

Any network functionality such as update checking should be obvious and limited.

# Architecture Direction

The current application began largely as one Python file.

As functionality grows, **do not continue indefinitely expanding `maintenance_goblin.py` into a monolith.**

Gradually migrate toward something similar to:

```text
src/
└── maintenance_goblin/
    ├── __init__.py
    ├── __main__.py
    ├── app.py
    ├── ui/
    ├── tasks/
    │   ├── sfc.py
    │   ├── dism.py
    │   ├── chkdsk.py
    │   ├── cleanup.py
    │   └── optimize.py
    ├── services/
    ├── reporting/
    ├── config/
    └── utils/
```

Do this incrementally rather than rewriting functioning code unnecessarily.

Maintenance operations should ideally expose structured results rather than directly manipulating GUI widgets.

For example, conceptually:

```text
TaskResult
- task
- status
- summary
- raw_output
- duration
- warnings
- error
```

This will make GUI, CLI, reports and tests share the same underlying functionality.

# Immediate Goal

The immediate goal is to turn the current functioning prototype into a credible **v0.1.0 public GitHub release**.

Before introducing major new features:

1. Audit the current repository.
2. Understand the existing implementation before changing it.
3. Identify bugs, duplicated code and architectural problems.
4. Verify all maintenance commands behave safely.
5. Verify thread-safe GUI behaviour.
6. Verify administrator elevation.
7. Verify PyInstaller packaging.
8. Improve the visual polish.
9. Ensure documentation accurately describes implemented functionality.
10. Add appropriate tests where practical.
11. Prepare the GitHub release and GitHub Pages site.

Preserve working functionality during refactoring.

Do not perform a giant rewrite unless there is a compelling technical reason.

When making changes, explain significant architectural decisions and keep commits logically scoped.
